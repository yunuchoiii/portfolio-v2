## 서비스 성격

- 운동·휴식 시간과 반복 횟수를 미리 정해 두면, 화면을 보지 않아도 소리·진동·잠금화면 알림으로 다음 동작을 알려주는 운동 인터벌 타이머 앱입니다.
- 간단한 타이머 기능도 구독으로 막아 둔 앱이 많아서, 광고·결제·로그인 없이 모든 기능을 무료로 쓸 수 있게 만들었습니다. 데이터는 기기 안에만 저장합니다.
- App Store에 출시해 운영하고 있으며, 한국어·영어·일본어·중국어(간체)를 지원합니다.

## 나의 역할

- 기획·디자인·개발·스토어 출시·운영까지 1인으로 진행
- **React Native + Expo** 기반 iOS 앱 설계 및 전 영역 개발
- 백그라운드에서도 끊기지 않는 **타이머 엔진**과 **오디오·알림·진동 3계층 안내 구조** 설계
- **Live Activity(잠금화면·다이내믹 아일랜드)**, Apple 건강 앱 운동 기록 연동
- **Claude Code**와 협업하며 실기기 측정 → 원인 가설 → 검증 순서로 문제 해결

## 배경 및 문제

인터벌 타이머의 핵심은 "휴대폰을 주머니에 넣거나 화면을 끈 상태에서도 정확한 순간에 울린다"는 것입니다. 그런데 모바일 OS는 백그라운드 앱을 적극적으로 재우고 종료하기 때문에, 화면이 켜져 있을 때만 정확한 타이머로는 이 약속을 지킬 수 없었습니다.

- **OS의 백그라운드 제약:** 화면이 꺼지면 JS 타이머와 애니메이션 콜백이 멈추거나, 앱이 아예 종료될 수 있었습니다.
- **알림 시각의 오차:** 예약한 잠금화면 알림이 실제 구간 전환보다 한 박자 늦게 도착했습니다.
- **음악과의 공존:** 운동 중 음악을 듣는 사용자가 많아, 알림음이 음악을 끊거나 볼륨을 줄여서는 안 됐습니다.

그래서 <strong>"앱이 어떤 상태에 있든 정확한 시각에 다음 동작을 알려주는 타이머"</strong>를 목표로, 시간 계산과 안내 경로를 처음부터 백그라운드 기준으로 설계했습니다.

## 목표

- 화면을 꺼도, 다른 앱을 써도, 앱이 강제 종료돼도 어긋나지 않는 **절대 시각 기반 타이머**
- 소리·알림·진동이 서로를 보완하는 **다중 안내 경로** 구축
- 사용자가 듣던 음악을 멈추지 않는 알림음

## 나의 기여

### 1) 절대 시각 기반 타이머 엔진

`setInterval`로 1초씩 빼는 방식은 앱이 재워지는 순간 시간이 어긋납니다. 그래서 타이머 상태를 <strong>절대 시각 두 개(시작 기준 시각, 일시정지 시각)</strong>로만 들고 있도록 설계했습니다.

- **구간 전개:** 실행 시작 시 루틴 전체(웜업·운동·휴식·라운드·쿨다운)를 구간 배열로 펼치고, 현재 시각이 속한 구간을 매번 다시 계산합니다.
- **자동 복구:** 백그라운드에 다녀와 여러 구간을 건너뛰었거나 앱을 껐다 켜도, 현재 시각만으로 정확한 위치를 찾아 이어갑니다.
- **소리 정렬:** 매 tick을 다음 초 경계에 맞춰 깨워, 숫자와 소리가 흔들리지 않게 했습니다.

### 2) 오디오 · 알림 · 진동 3계층 안내 구조

- **오디오 세션:** 백그라운드 오디오 모드와 무음 루프로 앱을 살려 두고, 전화·Siri·알람이 끼어들었다 끝나면 다시 켭니다. `mixWithOthers` 모드로 다른 앱의 음악을 멈추거나 줄이지 않습니다.
- **로컬 알림:** 앱이 종료돼도 안내가 끊기지 않도록 구간 전환 시각을 미리 예약합니다. iOS의 예약 알림 64개 제한에 맞춰 가까운 구간부터 예약하고, 시작·재개·구간 이동·백그라운드 전환마다 다시 세웁니다.
- **알림음 설계:** 음악의 중저역과 겹치지 않도록 2\~3kHz 대의 짧고 날카로운 톤을 직접 생성했습니다.

### 3) Live Activity — 앱 밖에서 흐르는 타이머

- 잠금화면과 다이내믹 아일랜드에서 남은 시간·현재 단계·다음 순서를 보여줍니다.
- SwiftUI의 `timerInterval`·`pauseTime` API가 절대 시각으로 카운트다운을 그린다는 점에 주목했습니다. 이미 절대 시각으로 상태를 들고 있던 세션 모델과 그대로 맞물려서, **1초마다 갱신하지 않고 구간이 바뀔 때만 갱신**하도록 설계했습니다.

## 문제 해결

### 1) 화면을 끄면 몇 분 뒤 앱이 종료되던 문제

- **문제:** 화면을 끄면 1\~3분 뒤부터 알림음이 끊기고, 앱을 다시 열면 스플래시가 떴습니다. 처음에는 무음 루프 파일이 이어 재생되는 틈을 원인으로 보고 고쳤지만 증상이 남았습니다.
- **원인:** 실기기 크래시 리포트(`cpu_resource_fatal`, 53초 중 48초 CPU 사용)를 분석해 보니, 화면이 없는데도 링 진행 애니메이션이 매 프레임 돌아 iOS의 CPU 한도에 걸려 종료된 것이었습니다.
- **해결:** 앱이 백그라운드로 가면 애니메이션을 멈추고 값만 맞춰 두었다가, 다시 앞으로 오면 이어 그리게 했습니다. 시뮬레이터 측정에서 백그라운드 CPU 사용률이 **20\~30%대 → 4\~7%대**로 내려갔습니다.

### 2) 화면을 잠가도 CPU 125%로 돌며 발열이 생기던 문제

- **문제:** 한 시간 운동에 배터리 46%가 소모되고 기기 열 상태가 Serious까지 올라갔습니다.
- **원인:** 실행 화면의 안전장치가 네이티브 드라이버 애니메이션 값을 JS에서 읽으려 했는데, 그 값이 JS로 전달되지 않아 초기값에 고정돼 있었습니다. 안전장치가 계속 "어긋났다"고 판단해 화면 트리 전체를 매 프레임 다시 커밋하고 있었습니다.
- **해결:** 값을 바꾸는 쪽이 현재 값을 직접 기록하게 하고, 안전장치는 앱이 앞에 있을 때만 동작하게 했습니다. Instruments 측정에서 화면 잠금 상태 CPU 사용률이 <strong>124.8\~126.4% → 3.1%</strong>로 내려갔습니다.

### 3) 잠금화면 알림이 실제 전환보다 늦게 오던 문제

- **문제:** 예약한 알림이 실제 구간 전환보다 한 박자 늦게 도착했습니다.
- **원인:** expo-notifications의 날짜 트리거가 iOS 네이티브에서 "남은 시간" 기반 상대 트리거로 바뀌어, 예약 처리 지연이 그대로 얹히고 있었습니다. 코드를 바로 고치지 않고, 측정 절차와 결과별 처방을 먼저 문서로 정리한 뒤 라이브러리 네이티브 코드까지 확인했습니다.
- **해결:** iOS에서는 벽시계 기준의 캘린더 트리거로 바꿔 정해진 초에 울리게 했습니다. 이미 정확하게 동작하던 Android는 그대로 두었습니다.

## 배운 점

- **플랫폼 제약이 곧 설계 조건:** 모바일에서 "정확한 타이머"는 코드가 아니라 OS가 앱을 어떻게 다루는지 이해하는 데서 시작한다는 것을 배웠습니다. 절대 시각이라는 하나의 모델을 잡아 두니 백그라운드 복구, 알림 예약, Live Activity가 모두 같은 값 위에서 풀렸습니다.
- **재고 나서 고치기:** 증상만 보고 고친 첫 수정이 틀렸던 경험을 통해, 크래시 리포트와 프로파일러로 먼저 원인을 확인하는 습관이 생겼습니다.
- **AI와의 협업:** Claude Code와 함께 측정값·원인·판단 근거를 커밋과 문서에 남기며 일했고, 그 기록이 다음 문제를 푸는 출발점이 됐습니다.
