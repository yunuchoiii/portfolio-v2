## 서비스 성격

프랜차이즈 스터디카페 이용자가 자신의 학습 기록을 확인하고 동기부여를 얻을 수 있도록 구축한 웹뷰 기반 멤버십 서비스입니다. 인증과 카메라 등 일부 네이티브 기능을 제외한 앱의 핵심 경험(90% 이상)을 웹 기술로 구현했습니다.

## 나의 역할

- 인증·카메라를 제외한 전체 웹뷰 페이지(공부 기록, 리포트, 랭킹 등) UI/UX 개발
- 앱-웹 통신 규격(Bridge) 초기 설계 및 연동 구현
- 대량의 학습 데이터를 모바일에서 쾌적하게 볼 수 있도록 렌더링 성능 최적화
- 초기 웹뷰 도입 프로젝트로서의 기술 표준 및 UX 가이드라인 정립

## 배경 및 문제

스터디카페 이용자들에게는 단순한 좌석 결제를 넘어, 자신이 얼마나 공부했는지 확인하고 보상받는 '성취감'이 중요했습니다. 이를 위해 전용 앱이 필요했으나, 네이티브로 모든 기능을 개발하기에는 시간과 비용이 부족했습니다.
결국 수정과 배포가 유연한 웹뷰 방식을 택했으나, 다음과 같은 사용자 경험(UX) 문제가 우려되었습니다.

- **데이터 로딩 딜레이로 인한 성취감 저하:** 사용자가 공부 기록을 보러 들어왔을 때, 데이터 양이 많아 화면이 버벅거리거나 로딩이 길어지면 앱의 반응성을 신뢰하지 않게 됩니다.
- **웹사이트 같은 이질감:** 스크롤이 뚝뚝 끊기거나 터치 반응이 늦으면, 사용자는 이를 '앱'이 아닌 '모바일 웹사이트'로 인식하게 되어 서비스 몰입도가 떨어집니다.
- **기준 없는 개발로 인한 품질 리스크:** 팀 내 웹뷰 기반 앱 개발 경험이 전무하여, 초기에 명확한 UX/기술 기준을 잡지 않으면 결과물의 완성도가 현저히 낮아질 상황이었습니다.

따라서 <strong>"데이터가 많아도 가볍고 빠르게 느껴지는, 네이티브 앱 수준의 웹뷰 서비스"</strong>를 만드는 것이 핵심 과제였습니다.

## 목표

- 방대한 학습 이력 데이터를 모바일 환경에서도 끊김 없이 부드럽게 조회할 수 있는 성능 확보
- 인증 및 하드웨어 기능(카메라)을 제외한 모든 UI를 웹뷰로 통합하여 일관된 사용자 경험 제공
- 스크롤, 터치, 화면 전환 등에서 웹 특유의 이질감을 제거한 '앱스러운' UX 구현
- 향후 진행될 대규모 프로젝트(PTS B2C)를 위한 웹뷰 기술 표준 및 자산(Asset) 확보

## 나의 기여

### 1) 사용자 중심의 데이터 시각화 및 UI 구현

단순히 데이터를 나열하는 것이 아니라, 사용자가 모바일에서 직관적으로 정보를 소비할 수 있도록 UI를 최적화했습니다.

- **한눈에 들어오는 리포트:** 카드형 레이아웃과 요약 그래프를 활용하여, 좁은 모바일 화면에서도 사용자가 자신의 학습 현황(누적 시간, 랭킹 등)을 즉시 파악할 수 있게 설계했습니다.
- **일관된 네비게이션 경험:** 웹뷰 내에서의 화면 전환과 탭 이동 애니메이션을 통일하여, 페이지가 넘어갈 때마다 사용자가 길을 잃지 않고 자연스럽게 앱을 탐색하도록 유도했습니다.

### 2) 웹뷰 UX의 기술적 표준 수립 (First Mover)

팀의 첫 웹뷰 프로젝트로서, 맨땅에서 UX 품질 기준을 세우고 구현했습니다.

- **안정적인 뷰포트 제어:** iOS Safari의 주소창/툴바 이슈로 화면이 덜컥거리는 문제를 `dvh`, `svh` 단위와 `CSS safe-area` 설정으로 해결하여 단단한 레이아웃을 완성했습니다.
- **초기 로딩 경험 개선:** 데이터가 로딩되는 동안 빈 화면을 보여주는 대신, 스켈레톤 UI를 노출하여 체감 대기 시간을 줄이고 앱이 작동 중임을 명확히 알렸습니다.

### 3) 대량 데이터 처리를 위한 성능 최적화

학습 기록이 쌓일수록 렌더링이 느려지는 문제를 사전에 방지했습니다.

- **스마트한 캐싱 전략:** React Query를 도입하여 자주 조회하는 데이터(내 정보, 랭킹)는 캐싱 처리하고, 불필요한 네트워크 요청을 차단하여 화면 진입 속도를 획기적으로 높였습니다.
- **효율적인 렌더링:** `useMemo`, `useCallback` 등을 적재적소에 사용하여 리렌더링 비용을 줄이고, 리스트가 길어질 경우 가상화(Virtualization) 기법 등을 고려한 구조를 짰습니다.

### 4) 앱-웹 통신 브릿지 구조의 기초 마련

앱과 웹이 데이터를 주고받는 통로를 안전하게 구축했습니다.

- **초기화 프로세스 정립:** 앱 진입 시 토큰, OS 버전, 노치 유무 등의 필수 정보를 안전하게 넘겨받는 핸드쉐이크 로직을 구현하여, 로그인 풀림이나 UI 깨짐 없는 안정적인 시작을 보장했습니다.

## 문제 해결

### 1) 방대한 학습 로그 조회 시 UI 버벅임 해결

- **문제:** 사용자가 몇 달 치의 학습 이력을 조회할 때, 데이터가 많아 스크롤이 끊기거나 렌더링이 지연되어 사용자 경험이 불쾌해짐.
- **해결:** 데이터를 한 번에 모두 그리지 않고 필요한 만큼만 불러오는 구조와 React Query의 캐싱을 활용해, 데이터 양과 상관없이 언제나 부드러운 스크롤 경험을 제공.

### 2) 웹뷰 도입 초기, '웹 같은 느낌'으로 인한 몰입 방해

- **문제:** 터치 반응이 미묘하게 느리고, 화면 전환 시 깜빡임이 발생하여 사용자가 앱의 품질을 낮게 평가할 우려가 있었음.
- **해결:** 터치 영역을 네이티브 기준에 맞춰 확장하고, `active` 상태의 시각적 피드백을 즉각적으로 주도록 CSS/JS를 튜닝. 또한 초기 로딩 시 스켈레톤을 적용해 화면 전환의 이질감을 최소화함.

### 3) 통신 규격 부재로 인한 개발 비효율 및 오류

- **문제:** 앱과 웹 간의 데이터 교환 방식이 정의되지 않아 기능을 추가할 때마다 오류가 발생하고, 유지보수가 어려웠음.
- **해결:** 확장 가능한 브릿지 통신 패턴을 직접 설계하고 적용. 이 구조는 이후 진행된 더 큰 규모의 PTS B2C 프로젝트에서도 그대로 재사용될 만큼 탄탄한 기반이 됨.

## 성과 및 영향

- **성공적인 웹뷰 앱 서비스 런칭:** 네이티브 개발 리소스 부족 문제를 기술적으로 해결하며, 이용자에게 핵심 기능을 안정적으로 제공.
- **높은 서비스 안정성 달성:** 철저한 초기 설계와 테스트 덕분에 서비스 운영 기간 동안 오류 및 CS 리포트가 거의 발생하지 않는 '무결점'에 가까운 운영 기록.
- **기술적 자산 확보:** 이때 정립한 웹뷰 아키텍처, UX 패턴, 데이터 흐름 설계는 이후 회사의 주력 서비스인 PTS B2C 웹뷰 구축의 핵심 기반이 되어 개발 생산성을 크게 높임.

## 배운 점

- **데이터의 시각적 경험이 중요함:** 단순히 데이터를 보여주는 것을 넘어, '얼마나 빨리, 얼마나 보기 좋게' 보여주느냐가 사용자의 앱 만족도를 결정한다는 것을 배웠습니다.
- **초기 설계의 파급력:** 맨 처음 만든 브릿지 구조와 UX 패턴이 이후 프로젝트 전체의 뼈대가 되는 것을 보며, 초기 아키텍처 설계에 공을 들이는 것이 장기적으로 가장 효율적인 방법임을 깨달았습니다.
