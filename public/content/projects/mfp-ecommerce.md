## 서비스 성격

메디푸드플랫폼 앱 내에서 건강 관련 상품을 구매할 수 있는 웹뷰 기반의 이커머스 서비스입니다. 회사 최초로 시도된 '앱 내 웹뷰(In-App Webview)' 형태의 커머스 구축 프로젝트로, Flutter 앱 환경에서 동작하는 웹 쇼핑몰을 개발했습니다.

## 나의 역할

- **웹뷰 기반 커머스 전체 UI/기능 개발 (상품 목록, 상세, 장바구니, 주문)**
- PortOne(아임포트)을 활용한 모바일 간편결제 연동 및 결제 흐름 제어
- 커머스 UX 핵심인 이미지 로딩 속도 및 렌더링 최적화
- **플러터 개발자 부재 상황에서 앱 스킴(App Scheme) 설정 및 핸들링 로직 직접 구현**

## 배경 및 문제

기존 앱에는 상품 구매 기능이 없었고 비즈니스 확장을 위해 커머스 도입이 시급했습니다. 하지만 당시 **사내에 플러터(Flutter) 담당 개발자가 부재한 상황**이었고, 커머스 구현을 위해 필수적인 '앱-웹 연동'을 누군가 해결해야만 했습니다.

- **기술 공백 발생:** 결제 연동을 위해서는 앱이 웹뷰의 요청을 받아 외부 결제 앱을 띄워주거나, 결제 후 다시 앱으로 돌아오는 '스킴(Scheme)' 처리가 필수적인데 이를 구현할 모바일 개발자가 없었습니다.
- **결제 경험의 단절 우려:** 스킴 처리가 되지 않으면 결제 도중 화면이 하얗게 멈추거나(White Screen), 결제 완료 후 주문 페이지로 돌아오지 못하는 치명적인 UX 결함이 발생할 위기였습니다.
- **무거운 이미지 리소스:** 커머스 특성상 고화질 이미지가 많아 모바일 환경에서의 로딩 속도 최적화도 병행되어야 했습니다.

따라서 <strong>"프론트엔드 개발자로서의 영역을 넘어, 앱의 설정(Scheme)까지 직접 해결하여 끊김 없는 커머스 환경"</strong>을 구축하는 것이 목표였습니다.

## 목표

- Flutter 앱 내부에서 이질감 없이 동작하는 안정적인 커머스 웹뷰 구현
- 모바일 개발자의 공백을 메워, 결제 앱 연동을 위한 App Scheme 및 Intent 설정 완수
- 외부 결제 앱으로 이동했다가 복귀해도 결제 상태가 유지되는 견고한 결제 플로우 정립
- 이미지 최적화를 통해 초기 로딩 속도와 스크롤 반응성 대폭 개선

## 나의 기여

### 1) 앱 스킴(App Scheme) 직접 구현 및 결제 연동 (Ownership)

플러터 개발자가 없는 상황에서 프로젝트가 중단되지 않도록, 직접 모바일 설정을 학습하여 해결했습니다.

- **App Scheme 설정:** Android(`AndroidManifest.xml`)와 iOS(`Info.plist`) 설정을 직접 수정하여, 외부 결제 앱(카카오페이, 네이버페이 등)이 우리 앱을 다시 호출할 수 있도록 URL Scheme을 등록했습니다.
- **결제 흐름(Flow) 완성:** 웹뷰에서 발생하는 결제 요청을 가로채서 외부 앱을 실행시키고, 결제 완료 후 다시 앱으로 돌아왔을 때 웹뷰가 올바른 페이지(주문 완료)로 이동하도록 하는 핸들링 로직을 구현했습니다.

### 2) 끊김 없는 모바일 결제 경험 설계

- **예외 상황 방어:** 사용자가 결제 도중 취소하거나 앱을 강제 종료했을 때의 시나리오를 대비해, 장바구니 상태를 유지하거나 적절한 안내 메시지를 띄우는 방어 코드를 작성하여 결제 이탈률을 줄였습니다.

### 3) 사용자 경험을 좌우하는 이미지 최적화 (Performance)

상품을 탐색하는 사용자가 답답함을 느끼지 않도록 시각적 성능을 극대화했습니다.

- **포맷 및 사이즈 최적화:** WebP 포맷 도입과 CDN 파라미터 조정을 통해 이미지 용량을 획기적으로 줄였습니다.
- **체감 속도 향상:** Lazy Loading과 스켈레톤 UI를 적용하여, 화면이 뜨자마자 구조가 먼저 잡히고 이미지가 부드럽게 로드되도록 하여 사용자가 느끼는 대기 시간을 최소화했습니다.

### 4) 앱 제어를 위한 URL 규칙 정의

- **URL 패턴 기반 동작 설계:** 앱 내부 로직을 직접 건드리는 과정에서, 웹이 앱을 제어하기 위한 URL 패턴(예: `app://close`)을 명확히 정의하고 적용하여 네비게이션(닫기, 뒤로가기)이 꼬이지 않도록 만들었습니다.

## 문제 해결

### 1) 모바일 개발자 부재로 인한 결제 연동 불가 위기

- **문제:** 간편결제 연동을 위해서는 앱 레벨에서의 Scheme 설정과 Intent 처리가 필수적인데, 담당자가 없어 프로젝트 진행이 막힘.
- **해결:** "안 되면 되게 한다"는 마음으로 플러터와 네이티브 설정(Android/iOS) 문서를 직접 찾아보며 학습. 필요한 스킴 설정과 리다이렉트 처리를 스스로 구현하여 결제 기능 런칭을 성공시킴.

### 2) 외부 앱 이동 후 복귀 시 결제 흐름 유지

- **문제:** 간편결제를 위해 외부 앱으로 나갔다가 돌아왔을 때, 웹뷰가 어디로 이동해야 할지 판단하지 못해 흐름이 끊기는 현상 발생.
- **해결:** 결제 요청 시 Redirect URL을 명확히 설정하고, 앱 설정(Scheme)을 통해 돌아온 시점을 감지하여 웹 내부 라우팅을 분기 처리함. 이를 통해 사용자가 자연스럽게 '주문 완료' 페이지에 도달하도록 개선.

### 3) 고화질 상품 이미지로 인한 스크롤 버벅임

- **문제:** 상세 페이지에 긴 이미지가 많아 스크롤 시 렌더링이 밀리고, 데이터 소모량이 큼.
- **해결:** 뷰포트(Viewport)에 들어올 때만 이미지를 로드하는 Intersection Observer 기반의 Lazy Loading을 적용하고, 스크롤 중에는 이미지 디코딩 우선순위를 조절하여 부드러운 스크롤 경험을 확보.

## 성과 및 영향

- **기술적 한계 돌파 및 서비스 런칭:** 담당자 부재라는 악조건 속에서도 앱 설정을 직접 해결하여 회사 최초의 '앱 내 결제 커머스'를 성공적으로 오픈.
- **올라운더(All-rounder) 역량 입증:** 프론트엔드 영역을 넘어 모바일 네이티브 설정까지 다루며, 서비스 런칭을 위해 필요한 모든 기술적 문제를 해결하는 실행력을 보여줌.
- **웹뷰 기술 자산 확보:** 이때 맨땅에 헤딩하며 익힌 '스킴 처리'와 '앱-웹 통신' 지식은 이후 대규모 프로젝트(WithPTS 등)의 핵심 기반이 됨.

## 배운 점

- **경계 없는 문제 해결:** "내 분야가 아니다"라고 선을 긋기보다, 서비스 런칭이라는 목표를 위해 모바일 설정까지 학습하고 해결하는 과정에서 진정한 엔지니어링 마인드를 배웠습니다.
- **하이브리드 앱의 구조적 이해:** 앱과 웹이 어떻게 통신하고 상호작용하는지 밑단부터 직접 만져보며 깊이 있게 이해하는 계기가 되었습니다.
